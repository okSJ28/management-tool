# 第2開発管理ツール 仕様書

最終更新: 2026-10-29

---

## 1. システム概要

### 1.1 目的

開発プログラム（製造・詳細設計）の実績を一元管理し、規模・工数・品質の指標を自動算出する。
あわせて、担当者が日々の業務予定と実績を日次で記録し、チームの稼働状況を可視化する。

### 1.2 構成する2つのアプリケーション

| キー | 名称 | 用途 |
| --- | --- | --- |
| `dev` | 開発プログラム管理 | タスク単位の規模・工数・品質・スケジュール管理 |
| `plan` | 業務予定管理 | 担当者単位の日次予定／実績報告 |

画面左上のタブで切り替える。設定画面は両アプリで共有する。

### 1.3 動作環境

| 項目 | 要件 |
| --- | --- |
| サーバー | Python 3.10 以降。標準ライブラリのみで動作 |
| 追加ライブラリ | `openpyxl`（Excel 入出力を使う場合のみ。無くても他機能は動作） |
| クライアント | Chromium 系 / Firefox / Edge の最新版。ビルド・npm 不要 |
| コンテナ | `python:3.12-slim`、非 root（uid 10001）で実行 |

### 1.4 設計方針

- **機能の独立化** — API のエンドポイントは機能ごとに独立したモジュールへ分割し、自動登録する
- **層の分離** — HTTP 通信（`server.py`）／API（`api/`）／ドメイン・永続化（`core/`）を分ける
- **依存の最小化** — Web フレームワークを使わず標準ライブラリで実装する
- **エンコーディング安全** — Python ソースは ASCII を保ち、日本語ラベルは JSON 定義ファイルに置く

| `tool/api/features/*.py` | 各機能のエンドポイント定義 |
| `tool/core/config.py` | 環境変数・CLI 引数による設定 |
| `tool/core/db.py` | SQLite スキーマ、読み書き、列追加マイグレーション |

| `tool/core/excel_io.py` | Excel／CSV の読み書き |

### 2.3 リクエスト処理フロー

1. `Handler._dispatch()` が Host ヘッダを検証（`DPM_ALLOWED_HOSTS` が空なら無条件許可）
2. `/api/` 以外は `static_files.serve()` へ。GET / HEAD 以外は 404
3. 閲覧専用モードで GET / HEAD 以外なら 403 `read-only-mode`
4. `ROUTER.resolve(method, path)` でハンドラを解決
   - 未一致かつ同一パスに他メソッドが存在 → 405 `method-not-allowed`
   - 完全に未一致 → 404 `not-found`
5. ボディを読み込み（`DPM_MAX_BODY` 超過は 413）、`Request` を組み立ててハンドラを実行
6. 例外は `ApiError` → 指定ステータス、`JSONDecodeError` → 400、その他 → 500（詳細はログのみ、クライアントには `internal-error`）

### 2.4 機能モジュールの登録

`api/features/__init__.py` が `pkgutil` でパッケージ内のモジュールを列挙し、
`router` 属性を公開しているものを `api.build_router()` が統合する。
ファイルを追加・削除するだけで機能を増減できる。

```python
# tool/api/features/example.py
from ..http import Request, Response, json_response
from ..router import Router

router = Router()

@router.get("/api/example")
def example(_req: Request) -> Response:
    return json_response({"ok": True})
```

現在の登録数は 26 エンドポイント（`python server.py --routes` で確認可能）。

| データ | 内容 |

### 3.2 SQLite スキーマ

```sql
CREATE TABLE meta        (key TEXT PRIMARY KEY, value TEXT);
CREATE TABLE masters     (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- value は JSON
CREATE TABLE tasks (
    id TEXT PRIMARY KEY, seq INTEGER NOT NULL, type TEXT,
    program_id TEXT, project TEXT, assignee1 TEXT, assignee2 TEXT,
    start_date TEXT, end_date TEXT, created_at TEXT, updated_at TEXT,
    payload TEXT NOT NULL);                                             -- payload は JSON
CREATE TABLE plans (
    id TEXT PRIMARY KEY, seq INTEGER NOT NULL, kind TEXT,
    member TEXT, project TEXT, date TEXT, end_date TEXT,
    created_at TEXT, updated_at TEXT, payload TEXT NOT NULL);
CREATE TABLE entries     (member TEXT, month TEXT, value TEXT, PRIMARY KEY (member, month));
CREATE TABLE saved_views (seq INTEGER PRIMARY KEY, value TEXT NOT NULL);
CREATE TABLE users (
    id TEXT PRIMARY KEY, seq INTEGER NOT NULL, name TEXT, member TEXT,
    role TEXT NOT NULL, password TEXT NOT NULL,                         -- role: owner / admin / user
    created_at TEXT, updated_at TEXT,
    grade TEXT, manager TEXT);                                          -- 年次・担当管理者（空欄 = 未設定）
```

`users` は JSON 出力・JSON 復元・バックアップの対象外（復元でアカウントが消えないようにするため）。
`grade` / `manager` は後から追加した列で、既存 DB には起動時に自動で追加される（既存ユーザーは未設定）。

インデックス: `tasks(seq, type, project)` / `plans(seq, date, member)`

検索・集計に使う項目は実カラムに展開し、スキーマ駆動で増減する項目は `payload`（JSON）に格納する
ハイブリッド構成。`fields.json` を変更しても DB マイグレーションは不要。

#### 取組み予定（assignment）と日次入力の関係

```
assignment  「9/7〜9/18 SDLP341 製造（予定 40h）」
   │
   ├─ plan   9/8  予定 6h      ← assignmentId で参照
   ├─ result 9/8  実績 5.5h 進捗 70%
   └─ result 9/9  実績 7h   進捗 90%
```

ロールアップはクライアント側（`State.assignmentRollup`）で算出し、DB には保存しない。

| 項目 | 算出方法 |
| --- | --- |
| 実績積上 | 紐づく `result` の `actualHours` 合計 |
| 消化率 | 実績積上 ÷ `assignment.hours` × 100 |
| 進捗率 | 紐づく `result` のうち**最新日付の進捗率**（同一日なら `updatedAt` が新しい方） |

**ステータスの自動切替**（サーバー側 `Store._sync_assignment_status`）: 紐づく `result` が変わる保存（日次入力の一括保存・単票の登録／更新・削除・一括変更）のたびに、影響する取組み予定（保存・削除した記録の、変更前後の `assignmentId`）のステータスを次の値にする。紐づく `result` なし＝**予定**、あり＝**実施中**、上の進捗率（最新日付の進捗率）が 100＝**完了**。取組み予定のエディタで手で変えたステータスはそのまま保存するが、次に紐づく実績を保存したときに自動の値で上書きする。**中止** は手で選んだまま変えない。取組み予定そのものの保存では切り替えない

取組み予定を削除すると、紐づいていた日次行は残したまま `assignmentId` のみ解除される。
取組み予定は日次の集計（ダッシュボード「本日の業務予定」・予定サマリの工数）には含めない。

## 4. 計算仕様

すべて `core/model.py` の `compute()` で算出する。タスクの保存時、および
`GET /api/tasks` / `GET /api/bootstrap` の応答生成時に再計算される。

### 4.1 製造（mfg）

$$\text{換算step} = \begin{cases} \text{新規step} \times C_{new} & (\text{区分}=\text{新規}) \\ \text{母体} \times C_{base} + \text{修正step} \times C_{mod} & (\text{それ以外}) \end{cases}$$

$$\text{総工数} = \text{製造} + \text{チェックリスト} + \text{検証資料}$$

$$\text{テスト比率(\%)} = \frac{(\text{チェックリスト} + \text{検証資料}) \times 100}{\text{総工数}}$$

$$\text{生産性 新規} = \frac{\text{新規step}}{\text{製造工数}} \qquad \text{生産性 修正} = \frac{\text{修正step}}{\text{製造工数}}$$

$$\text{月換算生産性} = \frac{(\text{区分}=\text{新規 なら 新規step、それ以外は 修正step}) \times \text{monthHours}}{\text{総工数}}$$

換算step・月換算生産性は「開発プログラム一覧」Excel の数式（`IF(区分="新規", …)`）と同じく区分で式を切り替える。

$$\text{指摘合計} = \text{コーディング} + \text{チェックリスト} + \text{検証資料}$$

$$\text{品質(指摘/KS)} = \frac{\text{指摘合計} \times 1000}{\text{換算step}} \qquad \text{障害(件/KS)} = \frac{\text{障害件数} \times 1000}{\text{換算step}}$$

丸め: 換算step・総工数・生産性は小数2桁、テスト比率・月換算生産性は小数1桁、指摘合計は整数。

### 4.2 詳細設計（dd）

$$\text{総工数} = \text{詳細設計時間} \qquad \text{設計効率(頁/h)} = \frac{\text{頁数}}{\text{時間}} \qquad \text{品質(指摘/頁)} = \frac{\text{指摘件数}}{\text{頁数}}$$

製造専用の指標（換算step・テスト比率・生産性・品質・障害率）は `null` になる。

### 4.3 共通

- `durationDays` = 終了日 − 開始日 + 1（開始・終了が揃い、終了 ≧ 開始のときのみ）
- 分母が 0 または未入力の場合、結果は `null`（0 除算・NaN・Inf は出力しない）

### 4.4 実効ステータス（`effectiveStatus`）

`status` が明示されていればそれを採用。未設定の場合は日付から推定する。

| 条件 | 実効ステータス |
| --- | --- |
| 終了日 < 本日 | 完了 |
| 開始日 ≦ 本日 かつ（終了日なし または 終了日 ≧ 本日） | 進行中 |
| 開始日 > 本日 | 未着手 |
| 開始日なし・終了日なし | 未着手 |
| 開始日なし・終了日あり | 進行中 |

### 4.5 遅延判定（`isLate`）

実効ステータスが「完了」「対象外」以外で、かつ `終了日 < 本日` の場合に `true`。

### 4.6 値の正規化

| 対象 | 処理 |
| --- | --- |
| 数値 | NFKC 正規化 → カンマ・`%` 除去 → float。変換不能は `null`。真偽値は `null` |
| 日付 | `datetime` / `date` / 文字列（`/` `.` を `-` に変換）→ ISO `YYYY-MM-DD`。不正は `null` |
| 文字列 | 前後空白除去。空文字は `null` |
| 担当者名 | NFKC 正規化 → 空白除去 → `memberAlias` で置換 |
| Excel 見出し | NFKC 正規化 → 空白除去 → 小文字化して照合 |

### 5.2 主要エンドポイント詳細

#### `GET /api/bootstrap`

画面初期化に必要なすべてを返す。

```jsonc
{
  "schema":    { "types": [...], "fields": [...] },
  "enums":     { "status": {...}, "kubun": {...}, ... },
  "masters":   { "members": [...], "settings": {...}, ... },
  "tasks":     [ ... ],
  "plans":     [ ... ],
  "entries":   { "担当者名": { "2026-04": "完了" } },
  "savedViews":[ ... ],
  "folder":    "取込フォルダの絶対パス",
  "dataDir":   "データフォルダの絶対パス",
  "database":  "SQLite ファイルの絶対パス",
  "backupKeep": 30,
  "hasExcel":  true,      // openpyxl が利用可能か
  "readOnly":  false,
  "shared":    false,     // ループバック以外で待ち受けているか
  "updatedAt": "2026-09-08T17:53:43+09:00",
  "account":   { "id": "A250028", "name": "岡本 央渉", "member": "岡本", "role": "admin" },
  "memberAttrs": { "担当者名": { "grade": "1年目", "manager": "大場" } }  // 特権管理者を除くユーザーの属性。manager は管理者（特権管理者を含む）にのみ返す
}
```

#### `POST /api/tasks` / `PUT /api/tasks/{task_id}`

リクエストはタスク項目のオブジェクト。未知のキーは無視され、対象種別に属さない項目も除外される。
計算項目はサーバー側で上書きされる。

- プログラムID・案件名は両方必須。`POST` で空（空白のみを含む）なら 400 `task-required`。`PUT` と bulk `patch` は、送られてきたときだけ空でないことを確認する
- 数値の項目は 0 以上（負の値は 400 `invalid-number`）、進捗率は 0〜100（範囲外は 400 `invalid-progress`）
- Excel / CSV / JSON の取込はこの API を通らないため、これらの確認の対象外
- 応答: `{"task": { ... }}`
- 該当 ID なし: 404 `not-found`

#### `POST /api/tasks/bulk`

```jsonc
{ "action": "delete", "ids": ["id1", "id2"] }
{ "action": "patch",  "ids": ["id1"], "patch": { "status": "完了" } }
```

- 応答: `{"removed": n}` または `{"updated": n}`
- `delete` は管理者のみ。一般ユーザーは 403 `forbidden`
- 未知の `action`: 400 `unknown-action`

#### `POST /api/plans`

単票登録に加え、`dates` を渡すと同一内容を複数日へ一括作成する。

```jsonc
// 単票
{ "kind": "plan", "member": "山田", "date": "2026-09-08",
  "category": "製造", "title": "SDLP341 修正", "hours": 4 }
// 複数日
{ "kind": "plan", "member": "山田", "category": "会議", "hours": 1,
  "dates": ["2026-09-09", "2026-09-10"] }
```

- 応答: `{"plan": {...}}` または `{"plans": [...], "added": n}`
- `hours` / `actualHours` は `plan` / `result` で 0〜24、`assignment` で 0 以上。範囲外は 400 `invalid-hours`
- `progress` は 0〜100。範囲外は 400 `invalid-progress`（`/api/plans/batch`・`PUT`・bulk `patch` も同じ）
- `updatedBy` にログイン中ユーザーの担当者名が記録される
- 定例予定の登録は、担当者ごとに `dates`（指定曜日の日付一覧）と共通の `seriesId` を付けてこの API を呼ぶ。定例の「この日以降を削除」は `POST /api/plans/bulk`（`action: delete`）で行う

#### `GET /api/export/csv`

| クエリ | 既定 | 説明 |
| --- | --- | --- |
| `type` | `mfg` | `mfg` または `dd` |
| `ids` | （全件） | カンマ区切りの ID で絞り込み |

UTF-8 BOM 付き、改行 CRLF。ファイル名は `製造_一覧.csv` 等（RFC 5987 形式）。

#### `POST /api/import/excel`

```jsonc
{ "file": "開発プログラム一覧_R7.xlsx", "mode": "upsert", "withEntries": true }
```

- `file` は取込フォルダ直下のファイル名のみ。パス区切り文字や先頭 `.` を含む場合は拒否
- `mode`: `upsert`（既定）／`append`／`replace`。`replace` は管理者のみ（一般ユーザーは 403 `forbidden`）。`POST /api/import/csv` も同じ
- 応答: `{"added": n, "updated": n, "skipped": 0, "detail": {...}, "sheets": [...]}`
- 該当ファイルなし: 404 `file-not-found`

#### `POST /api/import/json`

```jsonc
{ "data": { "tasks": [...], "masters": {...}, "entries": {...} } }
```

含まれるキーのみ置換する。`tasks` を含む場合は**全タスクを置き換える**破壊的操作。
マスタ（設定）も上書きするため管理者のみ実行できる。`users` は含まれていても無視する。

### 5.4 認証・権限

| 項目 | 内容 |
| --- | --- |
| ログイン | ID とパスワード。失敗時は 0.6 秒待ってから 401 `login-failed` を返す（総当たり抑止） |
| パスワード保存 | PBKDF2-SHA256（12 万回、ソルト付き）。平文は保存しない |
| セッション | Cookie `dpm_session`（`HttpOnly; SameSite=Strict`）。ユーザー ID・有効期限を HMAC-SHA256 で署名 |
| 有効期限 | `DPM_SESSION_HOURS`（既定 12 時間）。期限切れは 401 `unauthorized` |
| 署名鍵 | 初回起動時に生成し `meta.authSecret` に保存 |
| 無効化 | 署名にパスワードハッシュを含むため、パスワード変更・初期化で既存セッションは無効になる |
| 初期ユーザー | `users` が空のとき `tool/core/users.json` から作成。初期パスワードは ID と同じ |
| 権限 | `owner`（特権管理者）／`admin`（管理者）／`user`（一般） |
| 属性 | 年次 `grade`・担当管理者 `manager`。選択肢はマスタ `userGrades` / `userManagers`（設定画面で追加・削除）で、空欄（未設定）可。一般・管理者のみ設定でき、特権管理者は保存時に空欄にする。マスタから外した値は設定済みのユーザーには残り（他の項目の更新でも消えない）、新たには設定できない |

特権管理者は管理者と同じ権限を持つ閲覧主体のユーザーで、担当者名を `excludedMembers` に登録し担当者から除外する（日次入力の入力対象・実績入力確認・担当者ビューなどの担当者一覧に表示しない）。日次入力などの既定の担当者は、ログインユーザーが担当者に含まれない場合は担当者一覧の先頭とする。

管理者（特権管理者を含む）のみ可能な操作:

- ユーザーの追加・編集・削除・パスワード初期化（`/api/users`）
- 設定画面（マスタ・計算パラメータ）の編集（`/api/masters`）
- JSON バックアップからの復元（`/api/import/json`）
- Excel / CSV 取込の全件置換（`mode=replace`）
- タスクの一括削除（`/api/tasks/bulk` の `delete`）

一般ユーザーはタスク・予定の登録・編集、Excel / CSV 取込（更新＋追加・すべて追加）、出力を利用できる。画面では全件置換の選択肢と一括削除ボタンを管理者にのみ表示する。
ただし業務予定（予定・実績・取組み予定、`/api/plans` 系）は、ログインアカウントの担当者名と一致する記録のみ登録・変更・削除できる（サーバー側で `forbidden-member`）。閲覧は全員分可能。画面では日次入力の担当者を自分に固定し、他の担当者の記録は閲覧専用で開く。
最後の管理者（特権管理者を含む）は降格・削除できない。自分自身は削除できない。

- アカウントバッジからアカウント情報の確認・パスワード変更・ログアウトができる

#### 6.2.1 一覧・入力の入力

- 一覧の上の「＋ 新規登録」でタスク編集ドロワー（全項目）を開く
- 各行の左（# の右）の「入力」列に操作ボタンを置く（横スクロールしなくても押せる）
  - 実績未入力（工数が 1 つも入っていない ＝ 総工数が空）の行は青い「実績入力」、入力済みの行は「編集」。⋯ は詳細ドロワー
  - 「実績入力」は実績入力ドロワーを開く。上にタスクの見出し（種別・プログラムID・案件名・区分・リソース区分・システム・担当者・期間。編集不可）を出し、入力欄は規模（step）・品質（指摘・障害）・工数のみ。「すべての項目を編集」で全項目のタスク編集ドロワーに切り替える（入力中の値は引き継ぐ）。削除・複製はできない
  - 「編集」はタスク編集ドロワー（全項目）を開く
- 着手済み（ステータスが未着手・対象外以外）で実績未入力の行は、ステータスの横に「実績未入力」を表示し、表示中の列のうち空いている実績の項目のセルを薄いオレンジにする。実績の項目は、製造が step（区分が新規なら新規step、それ以外は母体step・修正step）・指摘 3 種・工数 3 種、詳細設計が設計書頁数・指摘件数・詳細設計時間
- タスク編集ドロワー・実績入力ドロワー共通
  - 自動計算の項目は入力欄にせず、フォームの下に固定した「計算結果」に数値だけを表示し、入力に合わせてその場で更新する
  - 製造の step 欄は区分に合わせて、使わない欄を「入力不要」にする（新規なら母体step・修正step、新規以外なら新規step。区分が未選択なら対象なし）。ラベルに「入力不要」のマークを付け、入力欄は斜線の灰色で入力できない。保存時に入力不要の欄の値は消去する（値が残っているときはマークを「入力不要（保存時に消去）」にする）。分析・クロス集計の新規step・修正step の合計に、使わない欄の値が混ざらないようにするため
  - 使われていない項目（3.3 の `fold`）は「その他の項目」に折りたたむ
  - 見出しに番号（① 基本情報 ② 規模 …）と「入力済み N/M」を出す（M は表示中の欄の数。入力不要の step 欄は数えない。すべて入力済みなら緑）
  - プログラムID・案件名は両方必須。ラベルに「必須」のマークを付け、空いている欄をオレンジ枠にする。実績入力ドロワーでは、空いている実績の欄もオレンジ枠にする
  - 保存前に確認し、問題があれば保存せずに理由を表示する: プログラムID・案件名が空（前後の空白は除いて判定）、数値の項目が負、進捗率が 0〜100 の範囲外、終了日が開始日より前。実績入力ドロワーでプログラムID・案件名が空のときは「すべての項目を編集」から入力するよう案内する
  - 数値の欄は入力欄の右端に単位（3.3 の `unit`）を出す
  - 新規登録では、ログイン中の人が担当者（担当者一覧にいる）なら担当者①の初期値にする
- 一覧の表
  - 見出しの上にグループの色の帯（基本情報・期間・体制・規模・工数・品質・算出指標）を出す。合計の列（換算step・総工数・指摘合計）は元の入力のグループ、期間(日) は期間・体制、ステータスは基本情報の帯に含め、それ以外の算出指標は「算出指標」の帯にする。帯と見出しは縦スクロールしても上に固定する
  - 自動計算の列は見出し・セルとも灰色の背景にする（マウスを重ねると「自動計算（入力不可）」と式を表示）
  - 直接編集できるセルはマウスを重ねると ✎ を出す
  - 入力不要の step のセル（区分が新規の母体step・修正step、新規以外の新規step）は灰色にし、値がなければ「—」を出す。直接編集はできない
  - セルの直接編集でも編集ドロワーと同じ確認（必須・負の値・進捗率・期間）をする。区分を変えて入力不要になる step に値があるときは「…を消去します。よろしいですか？」と確認し、変更するとその値を消す（キャンセルなら区分も変えない）
  - 進捗率が未入力のセルは空欄にする（0% と区別する）。進捗率は使われていないため既定の表示列から外した（「⚙ 列表示」で表示できる。列の設定を保存済みの人はそのまま）
- 絞り込み
  - 1 段目に種別・キーワード・担当者・クイックを置き、案件・ステータス・区分・リソース区分・期間は「詳細条件」で開く 2 段目に置く（開閉の状態は保存。閉じていても、指定中の条件の数を「詳細条件（N）」と表示し、ボタンを青くする）
  - クイックに「自分の担当」（担当者①②のどちらかがログイン中の人）を追加。ログイン中の人が担当者のときだけ表示する
  - クイックの「工数未入力」を「実績未入力」に改名し、「実績入力」ボタンと同じ基準（総工数が空）にそろえた（従来は総工数 0h も含めていた）

### 6.3 業務予定管理

業務予定（予定・実績・取組み予定）は全員分を閲覧できるが、一般ユーザーが登録・変更・削除できるのは自分の担当者の記録のみ（5.4）。
他の担当者の記録を開いた場合、エディタは閲覧専用（「記録を表示」「取組み予定を表示」）で開き、保存・削除ボタンを出さない。
権限による画面ごとの動作の違いは [画面遷移図.md](画面遷移図.md) の 5.2 を参照。

#### 取組み予定（`planAssign`）

- 一定期間取り組む作業（`kind = assignment`）を担当者 × 日付のガント形式で表示。表示日数 14 / 28 / 42 / 60 日、「‹‹ 前へ」「今日」「次へ ››」で期間を移動
- 絞り込み: 担当者・ステータス・完了も表示
- 各行に予定h、実績h（紐づく日次実績の合計）、消化率、進捗（紐づく実績のうち最新日の進捗率）を表示。「未紐づけの実績」件数を KPI に表示
- **実績なしの強調**: 開始日が今日より前（開始日を過ぎた）で、紐づく日次実績（`result`）が 1 件もない取組み予定は、行を薄い赤の背景にし、左端に赤い線、作業内容の上に赤い「⚠ 実績なし」のラベルを付け、進捗の「実績未入力」を赤い太字にする。マウスを重ねると「開始日（…）を過ぎていますが、日次入力の実績が 1 件も紐づいていません」。ステータスが「完了」「中止」のものは対象外。紐づいているのが予定（`plan`）だけの場合も対象。表の下の凡例に説明を表示
- 「＋ 取組み予定を登録」／行クリックで取組み予定エディタを開く。エディタの担当者は一般ユーザーは自分に固定
- 取組み予定の新規登録はこの画面からのみ行う（日次入力には登録ボタンを置かない）
- エディタの「開発タスクと紐付け」は、担当者が担当（担当者1・担当者2）の開発タスクのみを候補にする。一般ユーザーは自分のタスク、管理者は選択した担当者のタスク（担当者を変えると候補を入れ替える）。既に紐付け済みのタスクは担当外でも候補に残す。日次記録エディタも同じ

**保存の仕組み**

- 1回の保存で予定・実績をまとめて `/api/plans/batch` に送る。実績は `sourceId` で同じ行の予定と結び付く
- 実績h・進捗率のどちらかが入っていれば実績ありとみなす。両方を空にして保存すると実績のみ削除する
- **未実施（予定していたがやらなかった作業）**: 予定の行で状況を「未実施」にすると、実績h・進捗率なしで保存でき、実績（`result`）は作らない（既存の実績は削除）。予定の状況を「中止」にし、進捗率（作業全体の進み具合。任意）と理由（`skipReason`。任意）は予定に残す。未実施を選ぶと実績h の入力は消す。未実施の予定は実績工数・平均進捗に数えず、終業前は入力済みとして扱う
- **未実施への自動切替**: 実績h に 0、または実績h が空欄で進捗率 0 を入れると、状況を自動で「未実施」にする。自動で未実施にした行（保存済みの進捗 0% の未実施を含む）は、0 以外の進捗率か 0 より大きい実績h を入れ直すと「予定通り」に戻す。手で未実施を選んだ行は、実績h（0 より大きい値）を入れると「予定通り」に戻す（進捗率だけなら未実施のまま）。未実施から他の状況に変えたときは、未実施の印の 0h・0% を消す
- **突発作業（予定外）**: 予定h が空欄・0 の予定の行に実績を入れた場合は、予定（`plan`）を作らず（既存の予定は削除）、`sourceId` のない予定外の実績として保存する。この場合は実績h（0 より大きい値）が必須
- **状況（予定通り / 遅延）**: 実績の `status` に保存する。進捗率とは連動しない（作業の完了は進捗率 100 で表す）。「遅延」のときは理由を `delayReason` に保存し、それ以外に変えると理由を消す。解消の記録（`delayResolvedAt` / `delayResolvedBy`）は、遅延のまま保存し直したときは保存済みの値を残し、遅延でなくしたとき・新たに遅延にしたときは消す
- ✕ で行を削除すると、予定・実績の両方を削除対象にする

**バリデーション**

- 工程（作業区分）は必須。未選択の行があると保存しない
- 予定外の行は実績（実績h または進捗率）が必須
- 予定h が空欄・0 の予定の行に実績を入れた場合（突発作業として保存）は、実績h（0 より大きい値）が必須
- 実績（`result`）は進捗率が必須
- 予定h・実績h は 0〜24。範囲外があると保存しない
- 進捗率は 0〜100。範囲外の入力は 0 / 100 に補正して欄にも表示する
- 全項目が空の行は保存対象から除外。既存行が空になった場合は削除する
- 保存中は再度の保存（ボタン連打・Ctrl+S 連打）を受け付けない
- **予定の合計工数のチェック**: 予定h の合計が基準（計算パラメータ「1人日あたり時間」、既定 7.5h）に足りない場合、保存時に「予定の合計が基準に足りません」の確認を出す。「このまま保存」で保存、キャンセルで中断。予定を変更していない保存（終業前の実績入力のみ等）では確認しない。予定なしの日・終日休暇の日（休暇日の扱いと同じ判定）は対象外

**未保存の変更の保護**

- 未保存の変更があるあいだは 20 秒ごとの自動同期で再描画しない
- 担当者・日付の切替、チーム入力状況からの切替、他の画面・アプリへの移動時に確認ダイアログを出す。ページを閉じる・再読込時はブラウザの離脱確認を出す

**入力状況の判定**：その日・その担当者の `plan` / `result` レコードが1件以上あれば「入力済」とみなす（別途フラグは持たない）。

#### 定例予定（日次入力・チーム予定ボードの「🔁 定例予定を登録」）

毎週決まった曜日の予定（例: 毎週木曜 0.5h 会議「課会」）を、期間内の各日の通常の予定（`kind = plan`）としてまとめて登録する。
登録した予定には共通の `seriesId` が付く。

| 項目 | 内容 |
| --- | --- |
| 担当者 | 一般ユーザーは自分に固定。管理者はチェックボックスで複数選択可（既定はログイン中の担当者） |
| 曜日（毎週） | 月〜日から複数選択 |
| 開始日・終了日 | 既定は今日〜90 日後。最長 1 年 |
| 工程・予定工数 | 必須。予定工数は 1 回あたりの時間（0 より大きく 24 以下） |
| 案件名・作業内容・PJCD・作業コード | 任意 |

- 入力中に「対象日 N 日（…）× M 名 → 予定を K 件登録します」をプレビュー表示
- 同じ日に同じ工程・作業内容の予定が既にある日は登録しない（二重登録防止）
- 祝日・会社休日は自動では除かない（休日マスタがないため）。不要な日は個別に削除する
- 日次入力では「🔁 定例」、チーム予定ボードでは「🔁」付きで表示。1 日分だけの変更・削除は通常の予定と同じ
- 記録エディタの「この日以降の定例を削除」で、その日以降の同じ定例予定をまとめて削除する（管理者は全担当者分、一般ユーザーは自分の分のみ）。入力済みの実績は残す
- 日次入力の未保存の変更があるときは登録できない（先に保存する）

#### 休暇登録（日次入力の「🏖 休暇登録」）

期間内の各日に、工程「休暇」の通常の予定（`kind = plan`）を登録する（`POST /api/plans` の `dates` 指定。サーバー側の変更なし）。

| 項目 | 内容 |
| --- | --- |
| 担当者 | 一般ユーザーは自分に固定。管理者は選択可（既定は日次入力で表示中の担当者） |
| 開始日・終了日 | 既定は日次入力の対象日。最長 1 年 |
| 区分 | 終日休暇（基準時間＝1人日、既定 7.5h）／午前休・午後休（基準時間の半分）／時間休（区分の右の欄に時間を入力。1 時間単位で 1h〜基準時間未満の整数（基準 7.5h なら 7h）。範囲外・小数・空欄は登録しない）。作業内容（`title`）に区分名、予定h（`hours`）に時間を入れる |
| 土日を除く | 既定 ON。祝日・会社休日は自動では除かない（休日マスタがないため） |
| 備考 | 任意（`note`） |

- 入力中に「対象日 N 日（…）→ 「区分」Xh を K 件登録します」をプレビュー表示。既に予定・実績がある日は日付を表示（残したまま休暇を追加する）
- 既に休暇を登録済みの日は登録しない（二重登録防止）
- 日次入力の未保存の変更があるときは登録できない（先に保存する）
- 日次入力のシート、チーム予定ボードの「＋ 予定を登録」、定例予定の工程の選択肢から「休暇」を外す。チーム予定ボードで登録済みの休暇を開いたときは「休暇」のまま表示・編集できる
- 前営業日の複製・前回の入力は休暇の日を飛ばし、休暇前の入力を対象にする（休暇の予定は複製しない）

#### チーム予定ボード（`planBoard`）

- 担当者 × 日付のマトリクス。表示日数 **本日** / 7（既定）/ 14 日
- 7・14 日表示: 「今日」で今日の 2 日前から表示、‹‹ ›› で 7 日ずつ移動
- **本日**（1 日表示）: 選ぶと当日の 1 日分だけを表示する。予定・実績の列を広げ（2 列なら各 360px、種別で 1 列にしたときは 560px。表は画面幅いっぱいに広がる）、カードを読みやすくする。‹‹ ›› で前日・翌日に 1 日ずつ移動し、「今日」で当日に戻る。本日から 7・14 日に切り替えると、表示していた日の 2 日前から表示する
- 各日付を **☀ 予定**・**🌙 実績** の 2 列に分けて表示（日付・列見出しは 2 段の固定ヘッダー）。種別で絞り込んだときはその種別の 1 列のみ
- 絞り込み: 担当者・工程（作業区分）・案件・**種別（予定／実績）**、横断検索と連動
- 担当者の属性での絞り込み: **年次**（全員）と **担当管理者**（管理者・特権管理者のみ）。選択肢はマスタ `userGrades` / `userManagers`（マスタから外した値も設定済みの担当者がいれば表示）と「（未設定）」。ユーザーの登録がない担当者・属性が空欄の担当者は「（未設定）」に入る。選んだ条件に合う担当者だけを行に表示し、担当者の選択肢も同じ条件で絞る（選択中の担当者が条件に合わなくなったら選択を解除）。該当者がいないときは「条件に該当する担当者がいません」。条件は画面を開いている間だけ保持する。一般ユーザーは最初に開いたときの年次の初期値を自分の年次にする（未設定なら「(すべて)」。切り替えた条件は他の画面から戻っても保持し、再読込で自分の年次に戻る）。管理者・特権管理者の初期値は「(すべて)」
- 表示: 予定 = 塗りつぶし、実績 = 破線枠 ＋ 進捗率。📌 取組み予定の帯は予定の列に表示。実績は元の予定と同じ並び順（予定外の実績は後ろ）
- **遅延の強調**: 状況「遅延」で解消を登録していない実績は、赤い太枠・薄い赤の背景にして先頭に「⚠ 遅延」のラベルを付ける。マウスを重ねると「⚠ 遅延：理由」を表示する。解消済みの遅延は通常の実績と同じ見た目にして先頭に緑の「✓ 遅延解消」を付け、マウスを重ねると「✓ 11/14 解消（登録者）」も表示する。担当者名の横に、**未解消の遅延の件数**を赤いバッジ（⚠2 など）で表示する。件数は表示中の期間に関係なく数える（工程・案件などの絞り込み条件は反映）。マウスを重ねると「未解消の遅延が N 件あります（表示中の期間より前の分も含む）」
- 未実施の予定（状況「中止」で実績のない予定）は予定の列に薄く表示し「未実施」と付ける（実績の列には出さない）。予定外（突発作業）の実績は実績の列にだけ表示する。マウスを重ねると「予定 3h（未実施：理由）」のように理由を表示する。ダッシュボード「本日の業務予定」は「5h → 未実施」、担当者ビューの本日の予定は「未実施」と表示する
- セル・チップのクリックや「＋ 予定を登録」で単票エディタ。空セルをクリックすると、その列の種別（予定／実績）で新規登録する。単票エディタのステータスは、種別が予定なら `planStatuses`、実績なら 予定通り / 遅延。実績の遅延は「遅延の理由」（`delayReason`）、予定の中止（＝未実施）は「未実施の理由」（`skipReason`）の欄を表示する。種別を切り替えると選択肢も切り替わる
- 「🔁 定例予定を登録」で定例予定を登録できる
- 一般ユーザーは自分の行の空セルのみ新規登録できる（他の担当者の行の空セルは反応しない。チップは閲覧専用で開く）
- CSV 出力（種別・対象日・工程・進捗率・状況・遅延理由・遅延解消日・未実施理由を含む）

#### 予定サマリ（`planReport`）

- 期間 From / To と集計軸（作業区分・担当者・案件・ステータス）を指定
- KPI: 記録件数（予定／実績の内訳）、予定工数、実績工数（消化率）、平均進捗率（完了〈進捗 100%〉の件数・遅延の件数〈うち未解消の件数〉）
- グラフ: 集計軸別の予定工数（横棒）、日別の予定／実績工数推移（折れ線）
- 集計表: 軸別の件数・予定工数・実績工数・消化率・構成比

## 7. 取込・出力仕様

### 7.1 Excel 取込

| 項目 | 内容 |
| --- | --- |
| 対象シート | 「製造」「詳細設計」（タスク）、「実績入力確認」（月次入力状況）。シート名は正規化して部分一致でも検出 |
| ヘッダ行 | 1〜15 行目から「プログラムID」を含む行を自動検出 |
| 列マッピング | `fields.json` の `excel` 別名およびラベルで自動対応付け。前方一致も許容 |
| 除外行 | 先頭セルが「例）」「例」「sample」で始まる行、プログラムID・案件名がいずれも空の行 |
| 終了判定 | 空行が 60 行続いた時点で打ち切り |
| 実績入力確認 | 「氏名」列と月列（1〜12）を検出し、`YYYY-MM` に変換。年度をまたぐ 1〜3 月は翌年扱い |

### 7.2 取込モード

| モード | 動作 |
| --- | --- |
| `upsert`（更新＋追加） | `種別＋プログラムID＋案件名＋開始日` が一致する行を上書き、無ければ追加 |
| `append`（すべて追加） | 重複判定せずすべて新規追加 |
| `replace`（全件置換） | 既存タスクをすべて破棄して置き換え（管理者のみ） |

### 7.3 CSV 取込

- 文字コードは `utf-8-sig` → `utf-8` → `cp932` の順に自動判別
- 1行目をヘッダとして Excel と同じ別名マッピングを適用
- 種別（mfg / dd）は画面またはリクエストで指定

### 7.4 出力

| 形式 | 内容 |
| --- | --- |
| CSV | 種別ごとに全項目。UTF-8 BOM 付き・CRLF のため Excel でそのまま開ける |
| Excel | 「製造」「詳細設計」シート（見出し装飾・ウィンドウ枠固定・オートフィルタ付き）、「実績入力確認」シート、「マスタ」シート |
| JSON | ストア全体のスナップショット。`POST /api/import/json` で復元可能 |

## 9. 運用

### 9.1 起動方法

| 方法 | コマンド |
| --- | --- |
| ローカル（Windows） | `管理ツール起動.bat` |
| 社内 LAN 共有 | `管理ツール起動(共有).bat` |
| 直接起動 | `cd tool && python server.py` |
| コンテナ | `docker compose up -d --build` |

`--share` 指定時は DNS リバインディング対策として、許可 Host を
`localhost` / `127.0.0.1` / `::1` / ホスト名 / ローカル IP に自動制限する。
ローカル起動時は `::1` でも待ち受ける（`localhost` が IPv6 に解決されるブラウザ対策）。

ポートが使用中の場合、`DPM_PORT_SCAN` の範囲で後続ポートを自動的に試行する。

### 9.2 データの保存とバックアップ

- 保存のたびに全体をトランザクションで書き直し、WAL をチェックポイントする。ユーザー情報の追加・変更・削除、`meta` の書き込み、起動時の列追加の後も同様にチェックポイントする
  → `store.sqlite3` を単体でコピーしてもデータが欠落しない
- 本番（coverity01）の更新デプロイ（`deploy/coverity01/deploy.ps1`）は、デプロイ前に `data/db-backup/store_YYYYMMDD_HHMMSS.sqlite3` を作成する（最新 10 世代）。コピーは SQLite のバックアップ機能で行い、WAL 上の未反映の変更も含める
- 同時に `data/backup/store_YYYYMMDD_HHMMSS.json` を書き出し、古い世代を削除する（既定30世代）
- 復元は「取込 / 出力」画面の「バックアップから復元」、または `POST /api/import/json`（管理者のみ）
- ユーザー情報（`users`）は JSON バックアップに含まれない。`store.sqlite3` のコピーで保全する

### 9.3 旧バージョンからの移行

初回起動時に `data/store.json` が存在すると自動的に SQLite へ取り込み、
元ファイルを `store.json.migrated` にリネームする。移行は1回のみ実行される。
DB に列が追加された場合は起動時に `ALTER TABLE` で自動追加する（例: `plans.kind`）。

**未実施・突発作業の記録の移行（1 回のみ）**: 起動後の初回読み込みで、予定に対応する実績のうち実績 0h（または実績h 空欄で進捗 0%）のものを削除し、予定の状況を「中止」（未実施）にして進捗率を予定に移す。予定h が空欄・0 の予定（休暇を除く）に 0h を超える実績が対応しているものは、予定を削除して実績を予定外にする。実行済みの印は meta `planNotDoneMigratedAt`。

**取組み予定のステータスの移行（1 回のみ）**: 起動後の初回読み込みで、取組み予定のステータスを紐づく実績から決めた値（上記の自動切替と同じ判定）に合わせる。手で選んだ値を戻さないよう、予定 → 実施中 → 完了 の向きにだけ進める（中止・実績のない実施中などはそのまま）。実行済みの印は meta `assignmentStatusMigratedAt`。

**実績の状況の移行（読み込みのたび）**: 起動後の初回読み込みのたびに、実績（`result`）の状況が「予定通り」「遅延」以外（実施中・完了・中止・予定・空など）のものを「予定通り」にする（変わったものがあるときだけ保存）。更新前の画面を開いたままの利用者が保存した値もそろえるため、毎回確認する。予定・取組み予定のステータスは変えない。最初に移行した日時は meta `resultStatusMigratedAt` に残す。

### 9.4 ログ

- 出力先: `data/server.log`（起動時に空にする）と標準出力
- 形式: `[HH:MM:SS] METHOD PATH -> STATUS BYTES ELAPSEDms`
- 所要時間には Keep-Alive の待機時間が含まれるため、実処理時間の指標としては使えない
- ローテーション機能は無い

## 10. 非機能・制限事項

### 10.1 実測値（タスク 221 件、ローカル環境）

| 処理 | 所要時間 |
| --- | --- |
| `GET /api/bootstrap`（約 225 KB） | 10〜100 ms |
| `GET /api/tasks`（約 211 KB） | 20〜40 ms |
| タスク1件の追加・更新 | 20〜40 ms |
| Excel 一括出力 | 約 85 ms |
| **Excel 取込（902 KB / 4シート）** | **約 58 秒** |

Excel 取込は openpyxl の読み込みが支配的で時間がかかる。
クライアント側のタイムアウトは取込系のみ 600 秒に設定している（他は 30 秒）。

### 10.2 制限事項

| 項目 | 内容 |
| --- | --- |
| 同時更新 | 全データをメモリに保持し保存時に全件書き直すため、複数人の同時更新は後勝ちになる |
| 書き込みコスト | 1件の更新でも全件（数百 KB）を書き直し、JSON スナップショットも生成する |
| データ量 | `bootstrap` が全件を返すため、数千件規模を超えると初期表示が重くなる |
| 認証 | ID とパスワードによる簡易ログイン。初期パスワードが ID と同じため、各自の変更が前提 |
| タイムアウト | `http.server` にリクエストタイムアウトが無く、低速クライアントに弱い |
| ログ | 無制限に追記される |

## 11. セキュリティ

### 11.1 実装済みの対策

| 対策 | 内容 |
| --- | --- |
| ディレクトリトラバーサル遮断 | 静的配信・Excel 取込ともに、正規化後のパスが基準ディレクトリ配下かを検証 |
| MIME スニッフィング防止 | 全応答に `X-Content-Type-Options: nosniff` |
| DNS リバインディング対策 | `DPM_ALLOWED_HOSTS` による Host ヘッダ検証（`--share` 時は自動設定） |
| リクエストサイズ制限 | `DPM_MAX_BODY`（既定 64 MB）超過は 413 |
| 例外情報の秘匿 | 想定外の例外はクライアントへ `internal-error` のみ返し、詳細はログに記録 |
| 閲覧専用モード | `DPM_READ_ONLY=1` で GET / HEAD 以外を 403 |
| ログイン認証 | `/api/health`・ログイン関連以外の API はログイン必須。パスワードは PBKDF2 でハッシュ化 |
| 権限制御 | ユーザー管理・設定編集・JSON 復元は管理者のみ（サーバー側で 403） |
| 更新者の信頼性 | 更新者はログイン中ユーザーから決定し、クライアントからの自己申告は使わない |
| 非 root 実行 | コンテナは uid 10001 で動作 |

### 11.2 インターネット公開前に必要な対応

| 重要度 | 課題 | 内容と対策 |
| --- | --- | --- |
| **高** | 初期パスワードが ID と同じ | ID を知っていればログインできる。各ユーザーにパスワード変更を徹底するか、初回ログイン時の変更強制が必要 |
| 中 | CSRF 対策が Cookie 属性のみ | セッション Cookie が `SameSite=Strict` のため別サイトからの書き込みは 401 になるが、同一ホスト（同一サイト）上の別アプリからは成立し得る。Origin 検証、または `Content-Type: application/json` の必須化が望ましい |
| 中 | セキュリティヘッダ不足 | CSP / X-Frame-Options / Referrer-Policy / HSTS が未設定 |
| 中 | バージョン情報の露出 | `Server: DevMgmt/2.0 Python/3.x` を返している |
| 中 | Host 制限が無効 | コンテナ既定は `DPM_ALLOWED_HOSTS=*`。実ドメインに限定すべき |
| 中 | TLS 未対応 | 平文 HTTP。リバースプロキシでの TLS 終端が必須 |
| 中 | レート制限が無い | ログイン失敗時の遅延のみで、アカウントロックや DoS 対策は無い |
| 低 | ログ肥大 | ローテーションが無い |
